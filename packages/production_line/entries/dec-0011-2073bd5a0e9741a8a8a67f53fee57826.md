## Decision: separate repo for the simulator project

**Status:** Active

User is starting a new, separate deliverable: a production-line simulator, built with Claude Code, that:
- Captures its own requirements (including a set of UI requirements)
- Is implemented based on the Capella model (Production_Line_Equipment_Model)
- Uses a routine that pulls parameters from the model to update aspects of the simulation

**Options considered:**
1. Create a new GitHub repo (e.g. `Production_Line_Simulator`), registered/scoped to this agent, as its own notebook
2. Reuse this repo (Production Line Repo) with a new `simulator` package alongside `production_line`

**Decision:** Option 1 — a separate repo. Rationale: this is a genuinely separate deliverable (a Claude Code implementation project with its own requirements and UI spec, plus a model-sync routine) rather than more modeling notes on the existing line/state-machine work, and it will be handed off to Claude Code as its own project, so a dedicated repo fits better than a package within this one.

**Next step:** user will create the GitHub repo and register/scope it to this agent via the Cartenza settings page. Once done, Cartenza will connect (clone_knowledge_repo, resuming if already GitHub-authorized) and set it up starting with a `purpose` entry.

**Reference:** DEC-0010 (current production-line model state), this repo's own `purpose` entry (for contrast — this repo stays scoped to the physical line/Capella model, not the simulator).

## Proposed package structure for the new simulator repo

Once the repo is created and registered, use this package structure:

- **`requirements`** — functional requirements for the simulator: what it needs to simulate, behavior expectations, scope boundaries, as the user captures them
- **`ui_requirements`** — the UI spec specifically: screens, controls, visualizations, interaction patterns. Kept separate from `requirements` since it's a distinct deliverable Claude Code will build against directly
- **`model_sync`** — the routine that pulls parameters from the Capella model (Production_Line_Equipment_Model) and updates simulation aspects: its design decisions, what it reads from the model, when/how it runs, and observations as it's built. Kept separate since it's the one piece that bridges back to the Capella model rather than being pure simulator logic — may hold a formal `routine_def` artifact once that's built out, per the Handbook's `routines` package guidance
- **`architecture`** — how the simulator itself is structured: tech stack choices, how Claude Code organizes the codebase, how the pieces (UI, sim engine, model-sync routine) fit together

**Next step once repo exists:** set the repo's `purpose` entry (in whichever package it's logged in, per convention), then start populating `requirements` as the user works through capturing them.

## Added: change_log package

- **`change_log`** — simulation-specific issues and decisions as they come up during build/use: bugs found, fixes applied, scope changes, anything that isn't a clean fit for `requirements` (which describes intended behavior) or `model_sync` (which is specifically about the model-pull routine). This is the catch-all for "something changed or broke, here's what and why," mirroring the role `lesson_learned`/`observation` entries have played in this repo (see LESSON-0001, LESSON-0002) but scoped to the simulator project specifically.
