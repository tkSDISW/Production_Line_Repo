### Slide 2 content

**Title:** AI-Assisted Line Recovery — Filling Station Example

**Scenario:** Filling Station reports state: Aborted

**What the AI does:**
1. Reads the state's own definition from the Capella model (the TR88.00.02-aligned description authored into the state): "The machine has faulted during Execute in a way that cannot be resolved by Hold or Suspend. The machine cannot leave this state except via an explicit Clear command."
2. Traces the state machine's transitions: what triggered Aborted (`abort`, self-reported to Line Control via Machine Status), and the only way out (`clear`)
3. Checks where the `clear` command is allocated in the functional architecture — finds it's wired only to the Operator Interface, never Line Control

**Recommended recovery:**
| Step | Action | Who |
|---|---|---|
| 1 | Diagnose the physical fault that caused the abort | Operator |
| 2 | Issue Clear → moves Aborted → Idle | Operator only |
| 3 | Issue Start → moves Idle → Execute | Operator only |

**Key takeaway (strongest line for the slide):**
"The model itself enforces the safety boundary — a fault can only be cleared by an Operator command, never automatically by Line Control. AI's role isn't to restart the line; it's to read the model, diagnose the correct path, and hand a human an exact, model-verified recommendation. Automation with a human still required to authorize."

**Test run this was based on:** live query against the actual pushed model (Filling Station's Aborted state, uuid 994078d8-18a1-4b9c-92ea-8a132b222418; clear transition allocated on FillingStation.OperatorControl per DEC-0009) — not a hypothetical, an actual demonstration of the pattern working end-to-end.
