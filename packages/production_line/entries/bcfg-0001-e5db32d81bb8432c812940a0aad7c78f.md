## Phase: from building the model to demonstrating it

This repo began as the working record of **building** a Capella model of a five-station bottling line. Its emphasis on PackML (ANSI/ISA-TR88.00.02) machine states and fault recovery is set out in the purpose entry.

The model is now substantially built (control-plane wiring complete for all five stations, DEC-0012). **The primary job has shifted to supporting demos of how to use the model**: showing how an engineer, or an AI agent, can read it, reason over it and recover a line from a fault, and how the notebook and Capella Fabric keep the model and the record consistent.

Calibrate accordingly:

- **Building-phase entries are settled history.** Do not rewrite them. Extend them with an addendum or supersede them with a new entry that references them.
- **New work is demo-driven.** Typical entries are demo scripts, rehearsal findings, model fixes found while rehearsing, and what the audience-facing story should say.
- **The model is the source of truth.** Anything an agent says on camera about states, transitions or who can issue `clear` must match what the model actually contains. Check the model; do not rely on memory or on earlier entries.

## Rigor

1. **Model-affecting claims are verified before they are logged.** Read the element via capella-fabric first. If a claim was not checked against the model, say so plainly in the entry.
2. **Model changes are small, named and logged.** Each patch gets a commit message and a matching decision entry giving what changed, why, and the capella-fabric commit. DEC-0014 is the pattern.
3. **Confirm UUIDs before patching.** Run `verify_model` after a patch. Push only on the user's confirmation.
4. **Record mistakes and recoveries.** A merge that dropped data, a diagram that would not open, or an overwrite from an unrefreshed local copy is a `lesson_learned`. These are the most reusable entries here and also good demo material (LESSON-0001, LESSON-0002).
5. **Demo-readiness is checked, not assumed.** Before a recording, verify that the diagrams named in the script exist, that element names on screen are correct, and that the narration matches what the screen shows.

## Entry conventions

- **Types:** `decision` for a choice made or a change completed. `observation` for something noticed or learned about the customer, tooling or standards. `lesson_learned` for a mistake and its fix. `note` for reference material, scripts and how-tos.
- **Cross-reference** related entries by ID (for example, "see DEC-0007, NOTE-0005"). Reference IDs, never paraphrase them.
- **Name conventions are decisions.** Model naming rules are already settled (qualify ExchangeItem names by machine, leave State names alone, `<Station>.<Role>Interface` for component exchanges: DEC-0007, NOTE-0005). Follow them and do not re-litigate them without a new decision entry.
- **Status line:** put `**Status:** Active` or `Superseded by <ID>` on decisions.
- **Entries are written to be read cold.** Someone who joins mid-project, or an audience watching a demo, should understand an entry without prior context. Keep entries concise, and put what was done and why before how.
- **Scripts that will be read aloud** (like NOTE-0010) keep narration separate from on-screen directions, and list their pre-recording checks at the end.

## Working with the model safely

- **Refresh the local Capella copy from the remote before editing in Capella.** Changes made through capella-fabric land on `master` from outside Capella, and an unrefreshed push has overwritten work before (DEC-0014, LESSON-0002).
- **Tool limits are documented, not worked around silently.** Creating exchanges and physical links, and creating state machines, are not supported by patch (OBS-0002). If a task needs them, say so and hand it to the user to do in Capella.
- **The agent recommends; a person authorizes.** This is the model's own stance on fault recovery, and it applies to how the agent behaves in demos too. In a demo the agent should explain what the model requires and never imply it can restart the line itself.
